## 5. 「点完当下就看得见」——这一轮的重点

判据不是"我看了一眼觉得行"，是三个数：抽屉矩形完全落在视口内、**抽屉底线 ≤ 输入框上沿**、余量为正。

```
390：抽屉 407→512，输入框上沿 676   → 余量 164 px
360：抽屉 385→490，输入框上沿 632   → 余量 142 px
```

输入框上沿不是硬编码选择器量出来的：脚本在视口底边（`elementFromPoint(w/2, h-6)`）探一个点，往上
找最近的 `position: fixed|sticky` 祖先，量它的矩形。两个宽度都找到了同一个 `div`（`sticky`，高 168 px），
`676 = 844 − 168`、`632 = 800 − 168` 也对得上——它是宿主钉在底部的那一栏。

对照第一轮：同一句话、同一个动作，第一轮那一版把抽屉停在 `739→844`（390）与 `695→800`（360），
也就是**贴着视口底边、整块躲在输入框后面**（`soak/round1-10c15a0/first-pass-framing-*.png` 就是那一刻）。
这一轮同一颗节点、同样的点法，抽屉落在画面中部。

## 6. 占位那段有没有把 dock 挤走

三件事分开记，不混着说：

**① 位置**：`room`（`.gw-progress-sheet-room`）在 DOM 里排在 dock **之后**（`roomAfterDock: true`），
几何上也紧贴其下——dock 底 730、`room` 顶 734，**相隔 4 px**（390）；360 同样 4 px。

**② 只在有列表摊开时存在**：摊开时 `roomPresent: true`；点第二次收起后 `roomPresent: false`；
用「收起」按钮收起后也是 `false`。它带 `aria-hidden="true"`，高度正好是 `35vh`
（390 时 295.39 px = 0.35 × 844，360 时 280 px = 0.35 × 800）。

**③ 决定性实验**：把 `room` 从 DOM 里拿掉、立刻原位放回，量 dock 的矩形。

```
390：dockTopWithRoom 680 · dockTopWithoutRoom 680 · delta 0
360：dockTopWithRoom 658 · dockTopWithoutRoom 658 · delta 0
```

一像素都不动。另一端要区分清楚：抽屉**自己**会把 dock 往下推 117 px（内容轨道 1221 → 1338），
因为抽屉插在 dock 上面；那是抽屉的高度，不是占位挤的。两件事分开量，才说得清"占位没改 dock 的位置"。

## 10. 没做到的（`NOT_RUN`，一条不藏）

1. **多行抽屉（4 行那种）**：这一轮的树里，所有可摊开的节点都只有 **1 行调用**（探测了中间往外 5 颗，
   `check_t2 / check_t1 / check_t3 / execute_t3 / review_t1` 全是 1 行），所以实现者提到的"四张"那一档
   没有复现。105 px 抽屉的余量 164/142 px 是真的；**换成 4 行（约 207 px）时会怎样，本轮没量**。
   占位给了 295/280 px 的滚动余量，够不够由你们判断。
2. **>720 px 那一侧**：这一版声明没改，本轮没复测；桌面那处叠压仍是故意不修。
3. **720/721 断点边界**：只测 390 与 360，没有逐像素找断点。
4. **`matchMedia` 的 `change` 监听**（拖窗口从宽到窄不刷新）：没验；两个宽度是同一页面改视口。
5. **「收起」按钮**：只在 390 上验（抽屉与列表归零、占位消失）；360 上没点它。
6. **同时摊开两组节点**：只摊开一颗。
7. **live 档案升级 / 重载 / 重启**：`NOT_RUN`（红线）。
8. **第一轮的读数没有重跑**：两轮各自对着自己的提交，没有交叉复测第二轮在 700 px 上的样子。
