string was sent through `POST /api/session/prompt`, which is a *message* submission, not a
composer submission: no command layer runs, so it arrived as an ordinary user message and
the gate classified it (`outcome: triaged-chat`, seq 9; `/grok status` the same, seq 30).
The mode record for run A therefore had to be written through the switch route
(`setBy: "switch:mode"`, seq 36 / seq 54). That is a statement about the transport, not
about the product, and F1 in §7 is corrected accordingly.

            <<<GROK-WORKFLOW-REPORT>>> 已给出验证标记：MARKER-F2-7731 … <<<END…>>>
    seq 29  request/header        tools: 101 (grok_close_block among them)
    seq 33  assistant/message     "已给出验证标记：MARKER-F2-7731 …"  (the gate's text, echoed)
    seq 35  turn/end              {"turn":1,"reason":{"kind":"completed"}}

So the mechanism is **not** "the user message is deleted before the model sees it" (the
first draft said that; it is wrong). The message stays in the transcript at seq 23 and the
model can read it. What the gate does is (a) take the message out of the inbox so it does
not drive the loop as a task, (b) answer it itself with one worker, and (c) tell the model
to relay that answer and call no tool. The consequence is the same either way: a handoff
never becomes a judgement turn, and `grok_close_block` is not called on it. A block close
therefore cannot happen with the gate on — which is why the block flow ran with it off:

    seq 54  plugin:grok-workflow/mode  {"v":1,"enabled":false,"turn":0,"setBy":"switch:mode"}

In run A that off-switch was thrown through the switch route because run A had no composer
(§4.1). With a composer, `/grok off` (seq 7–9) is the way a user does it, and it works.

## 7. Findings (all reproduced here)

**F1 — the raw API message path is not the command path; `/grok` typed in the composer
works.** (Corrected — see §9. The first draft claimed the command was unreachable.)
Typed into a real Chromium composer, `/grok on` produces
`command/run {"name":"grok","args":" on"}` (seq 4), then
`plugin:grok-workflow/mode {"enabled":true,"setBy":"command:/grok","workflowMode":"full"}`
(seq 5), then `command/done {"kind":"success"}` (seq 6); `/grok off` produces the same
three records with `enabled:false` and `setBy:"command:/grok off"` (seq 7, 8, 9); a second
`/grok on` produced seq 12, 13, 14. The earlier `triaged-chat` observation was my
transport: `POST /api/session/prompt` submits a *message*, so no command layer runs and the
gate classifies the text as chat (run A, seq 9; `/grok status`, seq 30). The command layer
sits in front of the composer's submit, not in front of the message API. Nothing about the
product is broken here: a user can turn the gate on and off from the composer, and the
record it writes is the same durable `plugin:grok-workflow/mode` record the composer switch
writes (`setBy` distinguishes the writer).

**F2 — with the gate ON, a four-line handoff is answered by the gate, so it never becomes a
judgement turn.** The gate does not delete the user's message — it stays in the transcript
and the model can read it (run B seq 23) — but the gate takes the message out of the inbox
(`removedCount 1`, seq 17), dispatches its own worker (`快速执行`, seq 19,
`outcome: full-escape-fast`), and then instructs the model to *"reply with the text between
the markers exactly as given … do not answer the request yourself, and do not call any
tool"* (seq 27). The model echoed the gate's answer and called nothing (seq 33), with
`grok_close_block` among the 101 offered tools (seq 29). The same shape appears on the
other tier in run A: `CAPTAIN SPLIT PREVIEW` + `outcome: full-escape-ask` (seq 42/43), and
there the model happened to ignore the instruction and call `grok_open_block` (seq 47), so
a *preview* can slip through — but no close can, because a close needs the user's handoff
to be the thing the model is working on. Block flow and the gate are mutually exclusive as
shipped: the block flow has to run with the gate off.

**F3 — a judge that answers in prose instead of calling `structured_output` is scored as
"no answer", and the block is vetoed as `监工调用失败`.**
Child `dc6863ac` (attempt 1 of `eda27615`) returned exactly the right JSON as **text**:

    [text] {"criteria": [{"text": "给出三条中文检查项", "met": true, …},
                         {"text": "把这三条检查项写进 work/checklist.md", "met": false, "evidence": []}]}

and the host reported `监工没有交出任何答案`, twice, then wrote
`监工调用失败：两次尝试都没有拿到可解析的逐条判断`. The successful child `c06feb79` did
call the `structured_output` tool. `parseSupervisorAnswer` can parse a JSON *string*
(`tryJson`, fenced or bare), but it is never reached, because the engine only surfaces a
value when the schema tool was used. Verdict row 3 is the result: `outcome: veto`,
`judged: true`, `criteria` all false, reason `监工调用失败` — an honest "no verdict", but
a real judgement lost to a format choice.

**F4 — `judged: true` is necessary but not sufficient.** It is computed as
`route !== 'deterministic'`, so a *failed* judge call also reports `judged: true` (row 3).
Anyone reading `judged` as "a model judged this" will be wrong; the distinguishing field
is the reason text (`监工调用失败` vs `监工认为…`).

**F5 — the model closes blocks on its own initiative.** After the foreman delivered,
the model called `grok_close_block` without being asked (block 1), inventing its own
four-line handoff. That handoff was accepted by the judge, but it means a soak that wants
to control the handoff must tell the model not to close — which worked for blocks 2–4
("交完等我发四行交接，不要自己关单").

**F6 — an undeclared write is invisible to the supervisor.** Block `6da4687d` was
approved "不写文件" (`writesPaths: []`), and its foreman nevertheless wrote three files
(`work/check1.log`, `check2.log`, `check3.log`, confirmed with `ls -l`). The close passed
with the warning `这一块批准的范围是「不写文件」，没有产物要查`. The scope check only
inspects paths declared in the task split, so a write nobody declared is not caught. The
warning is honest about the blind spot; nothing else is.

**F7 — the instance writes into the profile it runs on.** `session/selectModel` saved the
picked model as the profile default in `cordis.patch.yml` (+32 bytes), which is a third
delta in the clone that I did not make. Harmless here, but a soak that promises "only two
lines changed" has to check the file at the end, not just at the start.

## 9. Correction to the first draft of §4.1 and F1

The first version of this report said that `/grok on` never reaches the command layer, that
the session had zero `command/run` records, and that "a user who wants to turn the gate off
cannot" — presented as a product defect (F1), with a HYPOTHESIS that it was a 0.13.34
regression. **That was wrong, and it was wrong because of my transport.** In run A the
string was submitted through `POST /api/session/prompt`, which is the message API: no
composer, no command layer, so the text arrived as an ordinary user message and the gate
classified it as chat. The observation (`triaged-chat`, zero `command/run`) was real; the
conclusion drawn from it was not.

Run B tested the same string the way a user produces it — typed into a real Chromium
composer and submitted with Enter — and the command layer fired every time:
`/grok on` → seq 4/5/6, `/grok off` → seq 7/8/9, `/grok on` → seq 12/13/14, with
`setBy:"command:/grok"` and `"command:/grok off"` in the mode records. So F1 is rewritten as
a transport fact ("the raw API message path is not the command path"), the sentence "a user
who wants to turn the gate off cannot" is deleted because it is false, and the regression
HYPOTHESIS is deleted because there is no regression to explain.

The F2 claim was re-examined at the same time and its *mechanism* sentence was also wrong:
the gate does not delete the user's message before the model sees it — the message stays in
the transcript (run B seq 23) and the model can read it. What the gate does is take the
message out of the inbox, answer it with its own worker, and tell the model to relay that
answer and call no tool (seq 17/19/27/33). F2's *conclusion* survives, and is now proven on
the composer path as well: with the gate on, a four-line handoff produces a relay turn, not
a judgement turn, so a block cannot be closed. F2 stands on its own and does not depend on
the old F1.

What did not change: the two deliverables (a `judged:true` pass and a model-produced veto),
the `route:"inherit"` stretch result, the ledger rows, F3–F7, and the isolation facts.
