# `.tmp/mock` — 进度页手机分支树效果图

`mobile-tree.html` 是一张自包含的效果图（不进仓库、不进构建，`.tmp/` 已 gitignore）：
它用真实的 DSH 颜色 token 名、真实的 DOM 结构画**手机上应该长什么样**，叶子文字也是页面本来就有的那几句
（运行名、状态词、腿词、角标、任务标题、计数行、按钮）。分支线和收回线是用 JS 量出来的，不是手画的坐标——
换宽度、换字号，线会跟着走。

## 怎么打开

```bash
cd .tmp/mock && python3 -m http.server 8124
# 打开 http://localhost:8124/mobile-tree.html
```

三个宽度：默认 390px；`?w=360`、`?w=412` 看另外两档。单看一屏：`?only=waiting` / `?only=running` / `?only=done`
（配合浏览器缩放，一次看全一张手机）。

**推荐的手机屏宽度：390 CSS px**（iPhone 12/13/14 的逻辑宽度）。360px 是最窄一档，也要过。

## 三张屏各看什么

| 屏 | 状态 | 要看的东西 |
| --- | --- | --- |
| `shot-390.png` 第一屏（`?only=waiting`） | **① 等你点头**（waiting）—— 腿全是虚线，任务格只是排好位置 | 分支结构在「什么都没做」时也画得出来：分叉杆、收回杆都在，颜色只是灰 |
| `shot-390.png` 第二屏（`?only=running`） | **② 进行中**（running）—— 执行腿在跑第 2 个任务，第一格试了两次 | 重试：两颗点（琥珀 + 蓝）+ 中间虚线 + 角标「第 2 遍」；任务名整宽排在下一行 |
| `shot-390.png` 第三屏（`?only=done`） | **③ 已完成**（done）—— 腿全绿 | 汇总腿只走过一个任务 → 那张卡整行占满（分支侧 `none`），分叉/收回是**一根直竖线**，没有横杆 |

## 哪张图看得见分叉点、哪张看得见收回点

- **分叉点（腿 → 任务卡）**：`zoom-390-running.png`。看「规划」卡底边中点：一根 12px 竖茎往下，
  接一条横杆（从最左那张卡的中心到最右那张卡的中心），再从横杆往**每张卡顶边中点各落一根竖茎**，
  箭头正好停在卡片顶边上（不压边框）。三张卡的腿（规划/执行）：第 3 张卡在左轨第二行，
  它那根竖茎落在同一条横杆上，所以「1 左 2 右 3 左」是一棵真树，不是一列。
- **收回点（任务卡 → 下一张腿卡）**：同一张 `zoom-390-running.png`。看「执行」那张卡下方的横杆：
  每张任务卡底边中点先下一根 12px 竖茎，汇到一条横杆，再从横杆往下一张腿卡的**顶边中点**落一根竖茎。
  图里两个方向都在：上方是分叉（进卡），下方是收回（回腿）。
  同一条横杆带里，分叉杆在上（离上一行 8px）、收回杆在下（离上一行 16px），两根不会叠成一根。
- **最窄档 360px**：`zoom-360-done.png` + `shot-360.png`。两轨仍然是两轨，任务名可用宽度 **145px**（≥ 90px 的要求），
  最短的腿卡（只有一张任务卡的汇总）看得出来是整行。

## 每屏下面的绿字是当场量出来的读数

`页面 390px（内容 364px）· 任务名可用 160px · 横向溢出 无 ✓ · 横杆/竖茎 31 根`

- 「页面」是设备宽度，「内容」是 `.gw-progress` 自己的宽度；
- 「任务名可用」= 所有任务格里任务名那一行最窄的一个（就是「不许被挤」的那个数）；
- 「横向溢出」= 页面 `scrollWidth - clientWidth`，必须是 0；
- 「横杆/竖茎」= 这一屏画出来多少条 path。

三档实测（360 / 390 / 412）：

| 宽度 | 内容宽 | 任务名可用 | 横向溢出 | 结论 |
| --- | --- | --- | --- | --- |
| 360px | 334px | 145px | 无 | 两轨放得下，不需要降成单轨 |
| 390px | 364px | 160px | 无 | 推荐 |
| 412px | 386px | 171px | 无 | 更松，同样不溢出 |

## 这张图和真页面的关系

- 颜色只写 `--dsw-alias-*` token 名，值在文件顶部当**替身**给出。`--dsw-alias-border-l2` 替身比真实发丝线深一档：
  连线就是用它画的，100% 缩放下看不见的线没法评审。真页面里这些值由 DSH 给。
- 分支线和收回线在真页面里由 `measureProgressFlowWires()` 量矩形后画（同一层的 `svg.gw-progress-wires`），
  这张图用同样「读矩形」的办法画，只是为了证明几何成立，不是要替代那段代码。
- 卡片上的「分支侧」是 `data-gw-progress-branch-side`（`left` / `right` / `none`），和渲染函数里写下的
  属性同名同值：`none` 那张卡跨两轨。桌面矩阵不用它（那边是 `grid-row` = 任务号）。

## `verify.html` —— 同一套排版，换成**真 CSS + 真 DOM**

`mobile-tree.html` 是我自己写的 CSS 在画效果；`verify.html` 里一句我写的排版规则都没有：
它按宿主的方式加载浏览器包、用真组件渲染一次运行、把 stub 树序列化成 HTML，再把它套进**线上的
`progress.css`**（token 值仍用替身）。三张 iframe 分别 360 / 390 / 412 px——iframe 的视口就是这三档，
所以 media query 和量到的宽度不可能对不上。

```bash
node .tmp/mock/build-verify.mjs        # 生成 verify.html（读 src/client/index.js，不改任何东西）
python3 -m http.server 8124            # 或直接 file:// 打开（下图是 file:// + --allow-file-access-from-files 截的）
```

`verify-360.png` / `verify-390.png` / `verify-412.png` 是它三档的截图，页面上那行绿字是从帧里量出来的：

| 视口 | 页宽 | 任务名可用 | 横向溢出 | 卡顶 y（同排＝两卡同顶） | 分支侧 / 实际落轨 |
| --- | --- | --- | --- | --- | --- |
| 360px | 328px | **138px** | 无 ✓ | 252/252/346 · 498/498 | 完全一致 |
| 390px | 358px | **153px** | 无 ✓ | 同上 | 完全一致 |
| 412px | 380px | **164px** | 无 ✓ | 同上 | 完全一致 |

「卡顶 252/252/346」这一行是 `grid-row: auto !important` 干活的证据：第 1、2 张卡同一排，
第 3 张卡在第二排（346 − 252 = 94 = 卡高 + 24px 空档）。如果内联的任务号仍然生效，三张卡会是三排。

两件事这张图里看不到，属于另一层的责任：**连线**（`measureProgressFlowWires()` 在真页面的
`useEffect` 里量框、画 path；这个静态页没有 React 运行时，所以 `svg` 是空的），以及**焦点的呼吸动画**。
连线的形状看去 `zoom-390-running.png`（README 上一节）。
