## 4. 怎么驱动的，以及两个驱动方式上的事实（下一个人会踩同样的坑）

驱动方式：GUI 自己的 HTTP API（与上一轮 soak §4.0 同一条路），带浏览器会话 cookie：

    GET  /?token=<redacted>                        -> 303 + HttpOnly cookie
    POST /api/session/create    {"request":{"cwd":…}}
    POST /api/session/selectModel {"request":{"sessionId","provider","model","reasoningEffort"}}
    POST /api/session/prompt    {"request":{"requestId","sessionId","mode":"queue","content":[{"type":"text","text":…}]}}
    POST /api/userQuestions/answer {"agentId","callId","answer":{"answers":[{"id":"q1","selected":["确认"]}]}}

信封形状（这一轮试出来的，写下来省下一个人二十分钟）：`POST /api/<namespace>/<method>`，body 是
`{"type":"client-request","rpcId":"…","method":"<namespace>/<method>","payload":{"args":{…}}}`。
直接 POST 参数对象会被拒成 `Remote payload must contain exactly one plain-object args field`。

**F1（驱动面事实，不是产品缺陷）**：`userQuestions/answer` 只对 `state === 'continued'` 的问题有效，
否则返回 `false`。**前台窗口还开着的卡片**只能由真正接住 `user-questions/request` waterfall 的客户端
（Web GUI 里的浏览器）回答——没有任何 HTTP 路由可以回答一张还开着的卡片。第一版驱动在卡片刚出现时
就调 `answer`，拿到 `false`，于是空等了十分钟（`run-fix`/`run-fix2` 两个会话就是这么废掉的）。

**F2（模式面事实，决定了这个 bug 什么时候才会出现）**：Host 的 `tool-ask-user` 默认是 **legacy**
（阻塞、只认前台客户端，没有超时窗口），只有 `mode: timed` 才会在窗口过期后把工具结果写成
`{pending:true, callId}`，问题随之变成 `continued`，之后的答案才会以
`user-question-reply` 的 `user/message` 形式进入会话。**换句话说：在默认配置下，卡片答案永远不会变成
「用户消息」，它只是同一个回合里的一个工具结果**——那条路径既不需要也不受本次修复影响。本次修复覆盖
的是 timed 卡片（或任何窗口过期后仍可答的卡片）。soak 档案因此把提问工具改成 `mode: timed, timeout: 20`；
顶层的 `- id: tool-ask-user` 覆盖**改不动**预设里的那一行（试过，`request/header` 仍是
`['questions']`），能生效的是 `- id: preset-standard` + `config.plugins` 整份覆盖（bundle 里
standard 预设的 plugins 列表原样抄过来，只改 `tool-ask-user` 一项）。
