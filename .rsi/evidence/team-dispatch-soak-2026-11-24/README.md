# team-dispatch soak, 2026-11-24

Durable record of one isolated soak run against the built plugin of the rebased
`team-dispatch-v1`, plus the two differential probes that back the claim it
supports. The raw run lived in the gitignored scratch `.tmp/soak-td/`, which was
deleted after this copy was taken. Everything here was read out of those files or
measured on this machine; nothing is inferred.

Referenced from `docs/knowledge/VALIDATION.md` (entry: `team-dispatch-v1` rebase
to `main` `369d6e3`, 2026-11-24).

## 1. What was run, and against which build

One headless turn of `dsh` with the plugin mounted from a local build, driven by
`prompt-team2.txt`: the model had to call `grok_workflow` with exactly two
caller-supplied tasks, `write-a` (write `team_a.txt` = `TEAM_OK` with a real
shell command) and `read-b` (read it back, then write `team_b.txt` with
`TEAM_B_OK` and `A_SEEN=<what it read>`), then print each task's status and the
exact bytes of both files.

    size:    20683 bytes

The same `lib/index.js` bytes are in the merged tree this evidence was added to

## 2. Environment

- Isolated home: `DSH_HOME=<scratch>/dsh-home`, `HOME=<scratch>/home`, both under
  the scratch directory. Nothing outside the scratch home is written by the run.
- Profile: `headless-soak`, a fork of the `headless` profile
  (`package.json` name `dsh-profile-headless`, bundles `@deepseek-ai/dsh-base` and
  `@deepseek-ai/dsh-headless`). Its own patch layer is empty; the soak overlay is
  passed with `--patch`.
- Overlay `overlay-rebased.yml` (archived here, 1908 bytes): disables
  `llm-deepseek` and `llm-deepseek-account`, defines one provider `soak-live`
  (`api: openai-completions`, `baseURL: http://127.0.0.1:18088/openai/v1`,
  `apiKeyEnv: BIFROST_VIRTUAL_KEY`), points `agent-default-model` at
  `agent2api/deepseek-v4.1-flash`, enables `workflow-ptc` (`provider: spawn`), and
  inserts the plugin row `grok-workflow` mounted at the build's `lib/index.js`
  with `mode: full`, `grokDefault: 'on'`, `maxConcurrency: 2`,
  `timeoutMs: 1200000`, `childTimeoutMs: 420000`, `loopEnabled: false`, and all
  five roles (planner, worker, verifier, supervisor, synthesizer) on
  `soak-live` / `agent2api/deepseek-v4.1-flash`.
- Model: a real gateway model on the machine's own gateway, not a mock, not a
  stub.
- Key handling: only the environment variable NAME `BIFROST_VIRTUAL_KEY` appears
  in these files. `run.sh` sources the machine env file at
  `/home/fish/.dsh/bifrost.env` into the process environment; no key value is
  written to the transcript, to the overlay, or to anything archived here.
- The live instance and the live DSH home (`~/.dsh`) were not read, written,
  restarted, or reloaded at any point in this block.

## 3. Commands

The rig (`run.sh`, archived) was invoked as:

    cd <scratch>
    ./run.sh overlay-rebased.yml prompt-team2.txt soak-rebased.out

which is, step for step:

    export DSH_HOME=<scratch>/dsh-home
    export HOME=<scratch>/home
    set -a; . /home/fish/.dsh/bifrost.env; set +a      # key enters the process env only
    cd <scratch>/work
    timeout 1500 dsh --profile headless-soak --patch <abs>/overlay-rebased.yml "$(cat prompt-team2.txt)" \
      > <abs>/soak-rebased.out 2>&1
    echo "exit=$code elapsed=<s>s overlay=<abs> out=<abs>" | tee -a <abs>/soak-rebased.out

The overlay was generated by `gen-overlay.mjs` (archived); the file actually
applied is the archived `overlay-rebased.yml`, whose header line names the build
it mounts.

`NOT_RUN` in this block: the soak itself was not re-executed (it costs a live
model turn of about 8.7 minutes). The transcript and the checkpoints are the
record of the run that happened. What WAS re-executed in this block: both
differential probes (section 5 and 6), the `sha256sum` comparisons, and the
`taskboard` reference count.

## 5. Differential A: cross-process claim (lost update)

Rig: `lock-probe.mjs` (archived). It builds a fresh board with 12 `pending` rows
`t01`..`t12`, spawns 12 independent node processes, and each child opens its own
handle on the same board directory, waits for one shared start instant, then
claims its own row. A fresh handle then reads the board back and counts how many
rows survive in `in_progress`.

Measured in this block, 2026-11-24, 3 runs per side:

| side | taskboard `store.js` sha256 | children answering ok | rows in `in_progress` on disk | runs |
| --- | --- | --- | --- | --- |
| build main shipped before the durability fix (tag `v0.13.30`) | `a5e69bbe94088b702c41c35ce3082f748f80a118323d08f582126786913f6022` | 12 / 12, 0 child failures | **1 / 12**, 11 lost | **3 / 3** |
| the rebased build (this soak) | `18d1f72c8b90a02686d72b32ab584f4b300027a80931cbf083337d94ffb833e8` | 12 / 12, 0 child failures | **12 / 12**, 0 lost | **3 / 3** |

The surviving row on the losing side differed from run to run (`t02`, `t10`,
`t09`), which is what a whole-file rewrite from an in-memory snapshot looks like:
every process believes it won and reports success, and the last writer erases the
others. On the fixed side every claim re-reads the store under an exclusive claim
lock, so no row is erased.

Both sides were staged from git, not from this checkout's working tree:

    git archive v0.13.30 lib/taskboard | tar -x -C <stage>/v0.13.30
    git archive HEAD     lib/taskboard | tar -x -C <stage>/HEAD   # == v0.13.31 bytes

and the probe was pointed at `<stage>/<rev>/lib/taskboard/index.js`.

## 6. Differential B: arrival order

Rig: `order-probe.mjs` and `arrival-probe.mjs` (archived). Three rows are created
in the order `zeta`, `alpha`, `mid`; the board is then closed and reopened, and
the order is read back.

    v0.13.30 (pre-fix):  no `arrival()` on the board.
                         reopened list() = [alpha, mid, zeta]  = id order
                         arrivalPreserved = false
    rebased build:       `arrival()` present.
                         reopened arrival() = [zeta, alpha, mid] = creation order
                         arrivalPreserved = true
                         reopened list()   = [alpha, mid, zeta]  = still id order (contract unchanged)

So the pre-fix board could only answer in id order, and the rebased board answers
in creation order through `arrival()` while leaving `list()` as the deterministic
id-sorted view.

## 7. Honest boundaries

1. **The cancelled second run.** A second workflow run in the same headless turn
   was in flight when the turn ended. It is archived as
   `checkpoint-partial-unloaded-in-flight.json` (run id
   `0c8dcdb2-66d7-4db0-9ab2-6deda41e839f`, same session): `run.status = partial`,
   `cause = "the plugin was unloaded while the run was in flight"`, tasks
   `write-a:verified read-b:failed`. Cancelling in-flight runs on plugin unload
   and recording the run as `partial` is the required lifecycle behaviour; the run
   was not allowed to finish and its `read-b:failed` is not evidence about the
   code. It is not hidden here, and it is not a defect.
2. **What the soak does and does not prove.** It proves the plugin's workflow
   dispatch end to end against a real model: one turn, planner, two child tasks
   with real filesystem effects, independent verification, final answer, exit 0.
   It does NOT prove the taskboard or the dispatcher module, because neither is
   mounted into the plugin's runtime surface: `lib/index.js` in the build under
   test contains zero occurrences of `taskboard`
   (`grep -c -i taskboard lib/index.js` → `0`). Those two modules are proven by
   the direct probes in sections 5 and 6, which import
   `lib/taskboard/index.js` themselves. Module proven by probe; dispatch proven by
   soak; keep the two apart.
3. **The model is real, so the transcript is one sample.** `agent2api/deepseek-v4.1-flash`
   on the machine gateway is nondeterministic. The transcript is that run's record,
   not a repeatable string.
4. **Which codes the differential compares.** The 1/12 side is identified by the
   taskboard revision it installs (`store.js` sha256 `a5e69bbe…`), which is what
   tag `v0.13.30` carries. The current release `v0.13.31` carries the same
   taskboard bytes as the rebased build (`18d1f72c…`), so the fix is already in
   what main ships today: the pair compared here is pre-fix taskboard code against
   post-fix taskboard code, not two different `lib/index.js` builds (both sides'
   `lib/index.js` are plugin entry files that do not reference the module at all).
5. **The survivor count is not a constant.** `docs/knowledge/VALIDATION.md`
   already records the same differential against main at `369d6e3` and saw 5 / 6 /
   7 rows survive instead of 1. Both numbers were measured on this machine; the
   loss reproduces on every run, the exact number of survivors depends on the
   interleaving of the 12 processes. Do not quote 1/12 as a fixed property.
6. **Not re-executed here.** The soak was `NOT_RUN` in this block; only the
   probes, the hashes, and the reference count were re-run. Nothing in this file
   was taken on trust from the earlier session.
7. **What is not archived.** No `dsh-home` tree, no session directory, no log file,
   no credential, no key value. `run.sh` names the env file it sources and the
   overlay names the env var; the value is nowhere in this directory.
8. **Probe scope.** The claim probe uses one board directory on one local
   filesystem and advisory lock files. It says nothing about network filesystems,
   about a malicious actor who ignores the lock, or about `rename` durability
   beyond what the module itself documents.
