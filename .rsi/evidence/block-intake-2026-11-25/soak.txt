## 7. Failures, deviations, and what was not reached

**Deviation 1 — the plugin is a copied build, not a symlink to the worktree.**
The task said to symlink `node_modules/dsh-grok-workflow` at the worktree root. That
breaks the plugin: Node resolves the symlink's real path, so the plugin loads the
*repo's dev copies* of `@deepseek-ai/*` (0.2.1-rc.2) instead of the host's (0.2.2-rc.3),
and `/grok off` answered:

    Grok workflow toggle not changed: Receiver must be an instance of class Session. In this session no toggle was recorded.

(That message is V8 refusing a private-field access — `appendPluginRecord` calls
`session.#appendRecord`.) A package-shaped directory of symlinks to `lib/` and
`package.json` failed the same way, because `lib` was still a symlink. The fix was to
**copy** the worktree's build into the profile (`lib/`, `package.json`,
`cordis.patch.yml`, README/CHANGELOG/LICENSE, `docs/*.md`) with no local
`@deepseek-ai` — which is exactly the shape a real `dsh plugin add` install has
(the profile's own `.pnpm` contains zero `@deepseek-ai` packages). Verified the copy is
the same build: `sha256sum lib/index.js` matches the worktree byte for byte
(`4f362620eec94af3744901aea1afa66111bcf985d6746ba0b34d54dbf7280cac`), version reads
back `0.13.33`, `registerBlockTools` present. After that `/grok off` succeeded.
*This is worth a line in LOCAL-TESTING.md: "symlink the plugin root" is a trap.*

**Gap 2 — the model-backed supervisor could not run.** Its route is
`agent2api/deepseek-v4.1-flash` and that provider resolves `AGENT2API_API_KEY`, which
this isolated home does not have. Verdict attempt 2 says so and refuses to pass:

    监工调用失败：两次尝试都没有拿到可解析的逐条判断，这次不算通过

The deterministic gate still judged (attempts 1 and 3), so the verdict path is exercised
end to end; the *independent model judge* is not. The pass therefore carries
`judged:false`.

**Gap 3 — the first model route could not authenticate.** `GLM 5.3 Flash (tokenrhythm)`
answered `403 IDENTITY_VERIFICATION_REQUIRED 请先完成实名认证后继续使用` (AUTH). The chat
turn was retried on `muse-spark-1.3(oc)` and completed. That failed turn is still in the
session log (turn 1, `turn/end {kind:error}`) — it is visible in the screenshots as
「本轮运行失败 API 密钥无效」.

**Finding 4 — the confirmation card does not count as approval.** Answering
`ask_user_question` with 「确认」 is not a user message, so `grok_open_block(mode:"start")`
is refused with `approval-required`. The user has to type a plain message. A model that
politely uses `ask_user_question` for the confirmation gets bounced once. This is
reproducible and, as far as this soak can tell, not documented.

**Finding 5 — the handoff must be four *lines*, not four labels on one line.** The first
veto (attempt 1) fired on
`交接必须正好四行（做了什么 / 证据 / 没做 / 下一步），每行都要有内容` and
`交接的第二行（证据）为空或太短`. A single-line "做了什么：… / 证据：… / 没做：… / 下一步：…"
handoff is parsed as one line and vetoed. Re-sending it with newlines passed.

**Observation 6 — the composer's `workflow总开关` is not a trustworthy read of the session
toggle.** Right after `/grok off` it showed 关; after the next turn it showed
`开 · 全员模式` again, while the session log still had exactly one mode record,
`enabled:false`. The durable state and the gate's behaviour both say off; the switch's
label appears to fall back to the profile default (`grokDefault: on`). Not chased
further — reported because a user would read that switch as the session state.

**Not reached:** no `pass` with `judged:true` (needs `AGENT2API_API_KEY`); no block that
writes files (this block was approved as "不写文件", so the supervisor's own warning
`这一块批准的范围是「不写文件」，没有产物要查` applies); no multi-block split (the task was
a one-block split, so `splitHash` and the `blocks[]` array were exercised with one entry).
