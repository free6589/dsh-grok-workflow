== 10. why the gate fails, and what would make it pass ==

The tool computes `covered = COUNT - deliveryHistory.records.length`
(.rsi/tools/iterate-plan.mjs:466, 498). For this row that is 969 - 9 = 960, because the
history still holds six rows (#1-#6) whose scheduledAt is on the PREVIOUS rule's :01:50
cadence; only #7-#9 are occurrences of the current anchor DTSTART:20261120T073657Z.
Against 966 physically future occurrences (969 minus the 3 occurrences of this anchor
already due) the row would deliver rounds 39..1000 and still have 4 slots left, but the
tool never sees that: it subtracts all nine.

Consequences, stated plainly:
  * The row will not be reported ARMED again while its history carries the six legacy rows
    and COUNT stays 969; each new delivery pushes covered down by one.
  * The one call that clears the gate is an rrule edit to COUNT=971 keeping
    DTSTART:20261120T073657Z (971 - 9 = 962 = remaining, last occurrence
    2026-12-30T17:36:57Z, still <= 1000). This is a schedule_edit: arming stays the
    operator's, and this task's constraints forbid it, so it is reported, not performed.
  * The tool's own proposal is NOT equivalent: `--arm-spec` prints
    DTSTART:20261120T112852Z..COUNT=962 (section 3), which under the same subtraction is
    962 - 9 = 953 < 962 and would verify NOT_ARMED again. That inconsistency between
    `--arm-spec` and `--verify-row` is a tool-level finding, recorded here rather than
    reconciled by an edit.
