# dsh-grok-workflow 规格说明（v1 草稿，2026-11-24）

> 来源：本会话（fork）需求澄清三轮。用户是普通人（非计算机专家），要的是奇迹不是请示。

## 1. 一句话定位

本插件是一个**任务规划执行器**：主会话 AI 只管聊天，插件扛下所有长任务的拆活、派活、验收、续命。以前用户跟主代理直连干，时间长 bug 多；以后脏活累活全进插件。

## 2. 三条铁律

1. **聊天归主会话 AI**：插件永远不插话、不拦路、不念模板。用户只跟 AI 说话。
2. **权限拉满**：免费模型集合，不计成本。拆几块、用什么模型、怎么干，插件自主决策，不问用户。
3. **监工说了算**：做出来能不能用，监工验+真机跑过即算数，不需要用户点头。bug 零容忍，修好为止，不限返工轮数。

## 3. 架构（四层）

```
用户 ⇄ 主会话AI（队长，只聊天）
         │ 开工前大事报拆法（小事直接干）
    ┌────┴────┐
    ▼         ▼
 包工头A/B/C（同级并行，只分活验收，不写代码）
    ▼         ▼
 干活子代理（只认包工头）
 ── 监工（与包工头平级，挂队长下，一票否决 rounds）──
 ── 账本（垫底：每步落盘，断点续传）──
```

- **包工头**：分活、验收，不下场写代码；可再拆子代理。
- **监工**：独立一票否决，只认证据。跑偏了由监工纠，用户只管收。
- **账本**：关机/卸载/崩了，重开照账本接着干。目标断点续传，允许重做最后一小步，不许从头来。
- **惊喜**：插件懂的比用户多，应主动多给一版备选、顺手修周边 bug。不怕加戏，怕没戏。

## 4. 真机测试

- 默认 fork 用户环境当用户走一遍（慢但像用户），不只跑后台逻辑。
- 长任务每轮关键节点真机，至少发版前必真机。
- 测试标准三问：普通人能用？能不管它？像人吗？

## 5. 验收

- 监工验过 + 真机跑过 = 通过，不需用户点头。
- 用户只管收：成了叫用户，不成打回重做，用户随时一句话可叫停（但默认不用管）。
- bug 零容忍：发现就修，修好为止。

## 6. 待定（下一轮细化）

- 拆块上限（同时几块并行）。
- 监工否决后重做上限（建议不限，修好为止）。
- 账本保留时长与断点窗口。
- “大事报拆法”的大事标准（几步以上算大事）。
