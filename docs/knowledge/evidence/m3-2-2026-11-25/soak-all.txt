--- model routes: an environment adaptation, stated plainly -----------------

The clone carries no credential for the `agent2api` provider, and the live
profile's default chat model was `agent2api/spark-x2.6-low`. The first attempt
in scenario 1 therefore failed at the model boundary, not in the plugin:

  MISSING_CREDENTIAL  llm-pi-ai: no credential for provider route "agent2api";
  its profile resolves AGENT2API_API_KEY, which is not set …

No credential was copied out of the live home and none was read. Instead every
model route in the scratch profile was re-pointed at a provider the clone can
authenticate (BIFROST_VIRTUAL_KEY is present in this environment):

  agent-default-model          → bifrost-responses / opencode-go/muse-spark-1.3-contributor
  roles.worker/verifier/
    synthesizer/supervisor     → bifrost-responses / opencode-go/muse-spark-1.3-contributor
  guardianModel                → bifrost-responses / opencode-go/muse-spark-1.3-contributor
  (planner was already on that route)

Route liveness was checked before relying on it:
  $ curl -X POST http://127.0.0.1:18088/openai/v1/responses -d '{"model":
    "opencode-go/muse-spark-1.3-contributor","input":"say OK",…}'
  HTTP=200  time=1.64s

This changes only which model answers; it touches nothing the four scenarios
claim to measure (interception, run count, admission, heartbeat, uninstall).

--- claim A: a heartbeat is decided by the narrow listener -------------------

Status: NOT_RUN.

What it would need on this machine: an OPEN BLOCK in a session (blockIntake is
on, so the intake observer would be registered) plus a real heartbeat delivery
to that session, then a read of
$DSH_HOME/taskboards/grok-workflow/heartbeats-listen.jsonl for a `continued` or
`stopped` line and of heartbeats.jsonl for its absence/presence.

What actually happened: no scenario in this soak opened a block. The admission
probe (claim B) was refused with `mode-off` before any block existed, and
turning grok mode on, getting a user consent, opening a block and then waiting
for a heartbeat did not fit the time box. So:
  - $DSH_HOME/taskboards/ does not exist at all after every scenario;
  - neither heartbeats-listen.jsonl nor heartbeats.jsonl was ever written.
The absence is consistent with the design (both observers write only when a
session has an open block), but consistency is not evidence, so this claim is
NOT_RUN rather than CONFIRMED. It is the one part of the block this soak does
not pin.

--- claim B: admission is live (mode-off) -----------------------------------

Status: CONFIRMED.

A session that never turned grok mode on was asked, in its own words, to open a
block:

      '请立刻调用 grok_open_block 工具开一个块，目标是计算 2+2。必须真的调用这个工具，不要只解释。'

  tool/result isError=true

So the refusal is visible in the tool result itself, not inferred from the

consistent but is not what this claim rests on.

--- honest boundary --------------------------------------------------------

- The four scenarios ran against a CLONE with re-pointed model routes (above).
  That is the plugin's real code on a real harness with a real model, but it is
  not the live profile's exact model configuration.
- Scenario 2 did not run the literal command from the brief: `dsh --profile m32
  headless '<objective>'` exits 1 with "too many arguments. Expected 0 arguments
  but got 2: headless, …". The headless run used a sibling profile m32h with the
  same config and build and only the app bundle swapped
  (dsh-web-app → dsh-headless). The failure is recorded in soak-2-headless.txt.
- Scenario 3 could not adopt the killed session at all: `--session-id` is
  refused because the session journal contains `tool-workflow/guardian-start`,
  an event type this harness treats as unknown and not ignorable. That is
  pre-existing (commit 891b8a2), not an M3.2 change, and it is BLOCKED rather
  than worked around. The resume that did happen is a new run carrying a
  plugin-generated seed, not engine-level restore — which is what the design
  says resume means.
- Claim A (heartbeat) is NOT_RUN, as described above.
- Scenario 4 did not exercise a hot unload (removing the plugin from a running
  instance); the instance was stopped first. A node_modules symlink survives the
  removal and is reported as residue.
- No screenshots and no large dumps are kept: every file here is a command plus
  the extracted lines that carry the claim.
- No secrets: the web boot token appears nowhere in this directory (written as
  <REDACTED>), no API key value appears, and the only addresses used are
  127.0.0.1 and the provider proxy at 127.0.0.1:18088.
