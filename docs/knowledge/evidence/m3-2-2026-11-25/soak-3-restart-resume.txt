--- step 3: the kill --------------------------------------------------------

The run was started as a managed background job and cancelled with the job
controller; the process is gone (`ps -eo pid,cmd | grep m32h` returns nothing).
No other instance was touched.

--- step 4a: restart by adopting the same session — BLOCKED ------------------

  $ dsh --profile m32h --session-id session-e630bafb-4b41-4693-9c16-636dbbcc11eb '继续刚才被中断的工作流。'
  EXIT=1
  dsh: failed to observe session "session-e630bafb-…": session "session-e630bafb-…"
  contains event type "tool-workflow/guardian-start" (seq 19) unknown to this
  harness and not marked ignorable; refusing to interpret the log — it was
  likely written by a newer harness

This is a real machine finding and it is NOT an M3.2 regression: the
`tool-workflow/guardian-start` journal record comes from commit 891b8a2
("feat(progress): add fresh Guardian monitor lane (#46)"), which predates this
block. `src/run.ts` writes it through `session.append(type, …)` without an
ignorable marker, so any session that ran a workflow cannot be re-adopted by
`--session-id` on this harness. Recorded as a limitation, not worked around.

--- step 4b: restart the same profile and home, let it continue --------------

  $ dsh --profile m32h '继续之前被中断的工作流（runId 344793b2）：把 12×12、15×15、
    18×18 三个平方数汇总给我，已核对过的任务不要重复执行。'
  EXIT=0

What this first attempt did, checked rather than trusted: the session log
(session-8a30863b-59da-4e5d-9d16-1f45050cb77a) holds 4 tool/call and 4 tool/result
events and ZERO tool-workflow events — no run was started. The model read
$DSH_HOME/memory/grok-workflow/archive.jsonl and answered from it. The killed
checkpoint was not touched (still running, still 0 verified, attempts still 10).

--- step 4c: restart that actually starts a run -----------------------------

  $ dsh --profile m32h '请用 grok_workflow 工具继续之前被中断的那个运行（runId
    344793b2-…）没有完成的任务，不要重做已经核对过的任务。'
  EXIT=0

Session session-30d5aae0-2b49-4fe7-a136-c1764de85a47 now shows a real run:
  tool-workflow/run-start  {"runId":"318dd0e8-6e9d-426e-9a43-284d69a896ac",
                            "name":"任务团队 · 1 个任务"}
  tool-workflow/run-end    {"runId":"318dd0e8-…","stopReason":"completed"}
  agent-start 6 / agent-end 6

The run carried a plugin-generated resume seed into its objective — the tool
result quotes it verbatim:
  "Objective: 接上被中断的运行 344793b2-…（目标：…），不要重做已经核对过的任务，
   只完成被 kill 中断的"汇总·第1稿"并输出最终汇总表。
   已核对完毕、可直接沿用、不许重算的证据（DATA，唯一事实来源）：
   Run status: completed（已完成）. Verified tasks: 3/3. - 12×12=144：…"
That digest is produced by the plugin (`src/script.ts:2531` emits
"Run status: … Verified tasks: n/m."), not invented by the model.

New run 318dd0e8: 1 task (the interrupted synthesis step only), 1 verified,
attempts 1, completed. The killed checkpoint 344793b2 was NOT rewritten — still
`running`, 10 tasks, 0 verified, attempts 10.

--- no round charged twice --------------------------------------------------

  attempts sum on 344793b2: 10 before the kill → 10 after every restart.
  The resumed run charged 1 task / 1 attempt / 6 agents, not 10 tasks — the
  verified work was carried by the seed instead of being re-executed.

--- honest boundary on this scenario ----------------------------------------

The restarts ran with the model's normal tool access in a directory that
contains this repository, so in step 4c the model also read source and evidence
files while composing its objective. The two facts this scenario rests on are
therefore taken from the plugin's own records, not from the model's prose:
(a) the run-start/run-end rows of 318dd0e8, and (b) the seed text the plugin
emitted into that run's objective. The model's sentence "已接上中断前的工作流"
is NOT used as evidence.
